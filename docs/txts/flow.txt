A. APPLICATION STARTUP FLOW
--------------------------------------------------------------------------------

1. Backend Server Startup Flow (Python FastAPI / Uvicorn):
```
[1. Command Issued] (npm run server / uvicorn backend.app.main:app)
         |
         v
[2. Python Interpreter Boots]
         | - Loads sys.path with project root
         | - Imports backend/app/main.py
         v
[3. Pydantic Settings Loaded] (backend/app/core/config.py)
         | - Reads ROOT_DIR/.env and BACKEND_DIR/.env
         | - Initializes PORT (5000), HOST (0.0.0.0), MONGODB_URI, JWT_SECRET
         | - Creates UPLOAD_DIR (server/uploads) if missing
         v
[4. Lifespan Context Manager Entered] (backend/app/main.py:lifespan)
         | - setup_logging() establishes structured timestamped console logger
         | - Logs: "[NextCampus Server] Initializing FastAPI application..."
         v
[5. Database Connection Initialized] (backend/app/db/connection.py:connect_db)
         | - Instantiates AsyncIOMotorClient with 2000ms serverSelectionTimeoutMS
         | - Executes await client.admin.command('ping')
         |     * If Ping Succeeds: Sets _is_connected = True; logs success.
         |     * If Ping Times Out: Sets _is_connected = False; logs warning and
         |       enables in-memory fallback mode.
         | - If connected: Checks collection counts and executes _seed_collections_if_empty()
         v
[6. Middlewares & Routing Mounted] (backend/app/main.py)
         | - Attaches CORSMiddleware with allowed origins
         | - Mounts StaticFiles directory at /uploads
         | - Registers global exception handlers (HTTPException, RequestValidationError)
         | - Mounts create_api_router() on BOTH /api/v1 and /api prefixes
         v
[7. Uvicorn Socket Bound]
         | - Listens on http://0.0.0.0:5000
         | - Yields control in lifespan context; begins accepting HTTP traffic
```

B. USER INTERACTION FLOW
--------------------------------------------------------------------------------

1. Landing & Exploration Flow (Unauthenticated Visitor):
   - Visitor navigates to `http://localhost:3000/`.
   - `LandingPage.jsx` renders: Campus statistics (facilities, occupancy rates, solar
     microgrid yield), hero banner, and feature overviews.
   - User clicks "Launch Campus Map": Navigates to `/campus-map` where `CampusGisMap.jsx`
     renders public facility polygons and tactical 2D cartography.
   - User clicks "Sign In / Register": Navigates to `/auth`.

2. Authentication & Identity Flow:
   - User inputs email, password, and official university `enrollmentNumber`.
   - Registration triggers verification against the pre-loaded university enrollment database.
   - Upon successful signup or login, the client receives a signed JWT token.
   - Token is saved to `localStorage` under `nextcampus_token`.
   - User is redirected to `/dashboard` (Student Dashboard) or `/admin` (if administrator).

3. Authenticated Navigation Flow:
   - `AppLayout.jsx` renders persistent sidebar navigation:
     * Student links: Dashboard, Campus Map, Directory, SmartRooms, Care Complaints,
       SkillCampus, EcoCampus, AI Assistant, Profile Settings.
     * Admin exclusive links: Campus Management (Facility CRUD) and Complaint Administration.
   - Selecting a navigation link updates React Router state and renders the page
     smoothly without reloading the browser window.

D. DATABASE FLOW (CRUD LIFECYCLES)
--------------------------------------------------------------------------------

1. Create Flow:
   - Client sends JSON payload -> Pydantic validates required fields -> Service
     generates unique IDs/timestamps -> Motor issues `insert_one()` -> MongoDB
     commits document to disk journal.

2. Read Flow:
   - Client requests list with query parameters (e.g., `?category=academic`) ->
     Service constructs MongoDB query dictionary `{"category": "academic"}` ->
     Motor opens cursor with `.find(query).sort(...)` -> Returns list of documents ->
     Service sanitizes `_id` to string `id` -> Encapsulated in JSON envelope.

3. Update Flow:
   - Client submits updated fields -> Service constructs atomic update dictionary
     `{"$set": update_dict}` or array modification `{"$push": subdoc}` -> Motor
     issues `update_one({"_id": id}, update_spec)` -> Returns updated entity.

4. Delete Flow:
   - Client requests deletion -> Service checks for dependent entities (e.g., linked
     rooms in a building) -> If dependents exist and `cascade=false`, raises HTTP 409
     Conflict -> If confirmed with `cascade=true`, deletes children first via
     `delete_many()` then deletes parent via `delete_one()`.

+---------------------------------------------------------------------------+

G. ERROR FLOW & EXCEPTION HANDLING
--------------------------------------------------------------------------------

1. Client-Side Network Dropouts:
   - Wrapped by `src/services/api.js`.
   - If direct origin connection fails, automatically retries through Vite proxy
     (`/api/v1/...` and `/api/...`).
   - If completely unreachable, displays a clear toast: "Unable to connect to NextCampus
     API server. Please check your network or server status."

2. Validation Errors (HTTP 400 / 422):
   - Intercepted by `validation_exception_handler` in `backend/app/main.py`.
   - Converts raw Pydantic errors into readable messages listing exactly which fields
     were missing or invalid.

3. Uncaught Server Errors (HTTP 500):
   - Intercepted by `generic_exception_handler` in `backend/app/main.py`.
   - Logs detailed error stack trace to server logs.
   - Sanitizes client message in production to prevent leaking system internals:
     "An unexpected server error occurred. Please contact NextCampus IT Helpdesk."

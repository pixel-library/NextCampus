A. PROJECT INTRODUCTION
--------------------------------------------------------------------------------

NextCampus is an institutional smart campus operations platform and student digital
experience hub engineered for higher education universities and research academies.
It integrates campus cartography (GIS wayfinding), classroom IoT environmental
telemetry, rapid facilities maintenance triage (<45 min SLA), student hackathon and
project incubation, microgrid sustainability monitoring, and generative AI spatial
guidance into a unified, privacy-first interface.

Users interact with the platform across three primary interfaces:
1. Public Portal: Prospective students and visitors explore the interactive tactical
   campus map, inspect building directories, and review sustainability metrics.
2. Student Command Center: Authenticated students track personalized course schedules,
   find quiet study pods in the Central Library, lodge classroom maintenance reports,
   collaborate on peer projects, and query the AI copilot.
3. Administrative & Operations Console: Facility managers, campus security, and system
   administrators manage spatial GIS coordinates, triage incident tickets, assign
   technicians, order hardware spares, and monitor campus-wide rollups.


--------------------------------------------------------------------------------
B. COMPLETE SYSTEM OVERVIEW
--------------------------------------------------------------------------------

The platform functions through four tightly integrated tiers:
1. Client Presentation Tier: React 18 Single Page Application compiled by Vite 5.
   Implements client-side routing via React Router v6 and GIS mapping via Leaflet.
2. Application API Tier: Python 3.11 FastAPI asynchronous REST microservice running
   under Uvicorn. Validates requests with Pydantic and executes business rules.
3. Data Persistence Tier: MongoDB document database accessed asynchronously via Motor,
   supplemented by a thread-safe in-memory store for 100% decoupled offline testing.
4. Cloud Infrastructure: Hosted on Vercel (Frontend Edge CDN) and Render (Python ASGI
   Web Service), backed by MongoDB Atlas.

C. HOW THE FRONTEND WORKS
--------------------------------------------------------------------------------

1. Application Initialization:
- Entry point: `src/main.jsx`.
- Mounts the root component `<App />` into the DOM container `<div id="root"></div>`.
- Imports `src/index.css`, establishing CSS custom properties for the 5-color
  dark-licorice palette (`#191516`, `#382E31`, `#AC274F`, `#EB638B`, `#FFD9DA`).

2. Routing & Layout Frame:
- `src/App.jsx` wraps the application inside `<AuthProvider>` and `<BrowserRouter>`.
- Public routes (`/` and `/auth`) render directly without navigational framing.
- Authenticated routes are nested inside `<AppLayout />`, which renders:
  * Persistent Sidebar (`src/components/layout/Sidebar.jsx`): Dynamically shows
    student or administrator links based on `user.role`.
  * Top Navbar (`src/components/layout/Navbar.jsx`): Displays user greetings,
    notification indicators, and quick profile links.
  * Mobile Nav (`src/components/layout/MobileNav.jsx`): Displays a thumb-friendly
    bottom bar on small viewports.

3. State Management & Authentication:
- `src/context/AuthContext.jsx` manages user session state.
- Reads `nextcampus_token` and `nextcampus_user` from browser `localStorage`.
- Exposes `login(token, user)` and `logout()` helper functions.
- Custom hook `useAuth()` allows any component to access authentication state.

4. Interactive GIS Cartography:
- `src/components/map/CampusGisMap.jsx` wraps the Leaflet cartographic engine.
- Renders tactical 2D and isometric map projections.
- Displays campus facilities with custom SVG markers, polygon boundaries, and
  clustering.
- Provides interactive building search, category filters, and an admin editing toolbar
  that allows administrators to drag markers and persist new spatial coordinates.

5. API Communication Wrapper:
- `src/services/api.js` provides centralized network transport via `apiRequest`.
- Prepend base URL (`VITE_API_URL` or `http://localhost:5000/api/v1`).
- Injects `Authorization: Bearer <token>` automatically when logged in.
- Automatically handles `FormData` boundaries for image uploads.
- Implements fallback retries through Vite's development proxy if direct origin calls fail.


--------------------------------------------------------------------------------
D. HOW THE BACKEND WORKS
--------------------------------------------------------------------------------

1. Server Initialization & Lifespan:
- Entry point: `backend/app/main.py`.
- Configured with `lifespan` context manager:
  * Initializes structured logging.
  * Calls `connect_db()`: Connects to MongoDB, runs an admin ping, and seeds empty
    collections with canonical initial data.
  * Closes database connections cleanly on server shutdown.

2. Middleware Stack:
- `CORSMiddleware`: Permits requests from allowed frontend origins (`settings.CORS_ORIGINS`).
- `StaticFiles`: Mounts `server/uploads` at `/uploads` for image attachment delivery.
- Exception Handlers: Global handlers intercept `HTTPException`, `RequestValidationError`,
  and uncaught exceptions, formatting all errors into the NextCampus JSON envelope standard.

3. Router Architecture:
- Root router configured in `backend/app/api/router.py`.
- Groups 8 functional sub-routers: `/auth`, `/campus`, `/smartrooms` (and `/rooms`),
  `/care`, `/skillcampus`, `/sustainability`, `/ai`, and `/admin`.
- Mounted symmetrically on both `/api/v1` and `/api` in `main.py`.

4. Service & Data Separation:
- Route controllers parse HTTP parameters and delegate to `backend/app/services/*`.
- Services contain pure business logic and query MongoDB via Motor asynchronously.


--------------------------------------------------------------------------------
E. HOW THE DATABASE WORKS
--------------------------------------------------------------------------------

1. Database Engine:
MongoDB document database (`nextcampus`).

2. Collections & Roles:
- `users`: User profiles, bcrypt password hashes, and accessibility settings.
- `enrollments`: University admission registry for identity claim during signup.
- `locations`: Campus buildings, precinct zones, coordinates, and CAD floor schemas.
- `rooms`: Classrooms, lecture theatres, and quiet pods with live IoT telemetries.
- `complaints`: Maintenance incident tickets with public updates and private notes.
- `projects`: SkillCampus collaborative student teams and recruiting roles.
- `sustainabilities`: EcoCampus solar, water, waste, and carbon telemetries.
- `announcements`: Official campus alerts and bulletins.

3. In-Memory Failover:
If MongoDB is offline or unavailable during automated test suites, the application
automatically redirects operations to thread-safe memory arrays (`IN_MEMORY_*`),
ensuring zero test crashes.


--------------------------------------------------------------------------------
F. HOW APIS WORK IN THE PROJECT
--------------------------------------------------------------------------------

1. Internal REST API Envelope:
Every internal endpoint returns a consistent JSON envelope:
- Success: `{ "success": true, "message": "...", "data": ..., "meta": ..., "timestamp": ... }`
- Error: `{ "success": false, "message": "...", "data": null, "meta": { "errors": [...] }, "timestamp": ... }`

2. External AI API (Google Gemini 1.5 Flash):
- Integrated in `backend/app/services/ai_service.py` via HTTPX.
- Injects institutional context and returns structured rich cards.
- Automatically falls back to the internal Multi-Intent Heuristics Engine v4.5 if
  the API key is absent or external requests time out.

FEATURE 1: STUDENT ENROLLMENT & ACCOUNT CLAIMING
================================================================================
1. Feature Description:
Allows newly admitted students to register for NextCampus by claiming their pre-loaded
university enrollment record, preventing unauthorized account spam and role escalation.
2. User Trigger:
User clicks "Register" on `/auth`, fills in their name, email, password, and official
enrollment number (e.g., `MUR2502101`).
3. Frontend File: `src/pages/AuthPage.jsx`
4. Frontend Logic:
Validates that all form fields are non-empty. Dispatches `api.post('/auth/register', payload)`
via `src/services/api.js`.
5. API Endpoint: `POST /api/v1/auth/register`
6. Backend Processing:
`backend/app/api/routes/auth.py` invokes `auth_service.register_user`.
- Checks if enrollment number exists in `db.enrollments`.
- Checks if enrollment record has already been claimed (`isClaimed == True`).
- Forces `role = 'student'` to prevent self-assigned administrator privilege escalation.
- Hashes password using `bcrypt.hashpw()` with salt factor 10.
7. Database Operations:
- `db.enrollments.find_one({"enrollmentNumber": ...})`
- `db.users.insert_one(user_doc)`
- `db.enrollments.update_one(..., {"$set": {"isClaimed": True, "claimedAt": ...}})`
8. Final Response:
HTTP 201 Created returning `{ "success": true, "data": { "token": "...", "user": { ... } } }`.
9. Failure Cases:
- Enrollment number not in university database -> HTTP 400 "Enrollment number not found".
- Enrollment number already claimed -> HTTP 400 "This enrollment number has already been registered".
- Email already in use -> HTTP 400 "User with this email already exists".

FEATURE 2: INTERACTIVE GIS CAMPUS WAYFINDING & MAP EDITING
================================================================================
1. Feature Description:
Provides an interactive 2D and isometric GIS map with building search, category
filters, ADA step-free routing, and administrator coordinate editing.
2. User Trigger:
User navigates to `/campus-map` or clicks a building card from `/directory`.
3. Frontend File: `src/pages/CampusMap.jsx` & `src/components/map/CampusGisMap.jsx`
4. Frontend Logic:
Loads facility polygons and markers from `/api/v1/campus/locations`. Renders Leaflet
map tiles. Clicking a facility opens a modal showing departments, gross floor area,
CAD floor schemas, and linked classrooms. If logged in as admin, enables drag-and-drop
marker repositioning and saves updated coordinates.
5. API Endpoint: `GET /api/v1/campus/locations` & `PUT /api/v1/campus/locations/{id}`
6. Backend Processing:
`campus_service.get_all_locations()` queries MongoDB for active locations.
7. Database Operations:
`db.locations.find({}).sort("name", 1)`
8. Final Response:
HTTP 200 OK returning array of facility documents with coordinates and floorplans.
9. Failure Cases:
- Network dropout -> Map renders cached tiles; display toast warning.

FEATURE 4: CARE MAINTENANCE SLA TRIAGE & DUAL-NOTE PRIVACY
================================================================================
1. Feature Description:
Students report broken equipment in classrooms. Tickets automatically calculate Tier 1
Rapid Response SLAs (<45 min window). Administrators dispatch technicians, append
student-visible updates, and record confidential engineering diagnostics that are
strictly hidden from students.
2. User Trigger:
Student submits maintenance form on `/care`. Admin triages on `/admin/complaints`.
3. Frontend File: `src/pages/CareComplaints.jsx` & `src/pages/ComplaintAdmin.jsx`
4. Frontend Logic:
Form gathers issue category, location, priority, description, and optional photo.
Admin view displays technician dispatch drawer and internal notes tab.
5. API Endpoints:
- `POST /api/v1/care/complaints` (Create ticket)
- `POST /api/v1/care/complaints/{id}/assign` (Assign technician)
- `POST /api/v1/care/complaints/{id}/internal-notes` (Admin private diagnostic)
- `GET /api/v1/care/complaints/{id}` (View ticket details)
6. Backend Processing:
`care_service.py`: Generates human-readable ticket ID (`#CMP-xxxx`). Assigns SLA window.
When returning ticket to a student, explicitly redacts `internalNotes` from the document.
7. Database Operations:
- `db.complaints.insert_one(complaint_doc)`
- `db.complaints.update_one({"_id": id}, {"$push": {"internalNotes": note}})`
8. Final Response:
HTTP 201 Created on submission; HTTP 200 OK on updates.
9. Failure Cases:
- Student attempts to append internal note -> HTTP 403 Forbidden.

FEATURE 8: ADMINISTRATIVE FACILITY CRUD & SAFE CASCADING DELETION
================================================================================
1. Feature Description:
Allows administrators to manage buildings, departments, and floor specifications,
protecting against accidental orphaned classroom deletions.
2. User Trigger:
Admin creates, updates, or deletes a building on `/admin/campus-management`.
3. Frontend File: `src/pages/CampusManagement.jsx`
4. Frontend Logic:
Displays full facility inventory table with edit and delete actions.
5. API Endpoint: `DELETE /api/v1/campus/locations/{id}?cascade=false`
6. Backend Processing:
`campus_service.delete_location()` counts linked rooms matching `buildingCode`.
If rooms exist and `cascade=false`, aborts with HTTP 409 Conflict. If `cascade=true`,
recursively deletes dependent rooms before deleting the facility.
7. Database Operations:
- `db.rooms.count_documents({"buildingCode": code})`
- `db.rooms.delete_many({"buildingCode": code})`
- `db.locations.delete_one({"_id": id})`
8. Final Response:
HTTP 200 OK with `{ "deleted": true, "removedRooms": count }`.

--------------------------------------------------------------------------------
N. KNOWN LIMITATIONS & TECHNICAL DEBT
--------------------------------------------------------------------------------

1. Ephemeral Upload Storage on Free Render Tiers:
Maintenance photo attachments are saved to local disk in `server/uploads`. On free
cloud dynos, this storage resets upon redeployment. Production scaling should mount
an S3 or Cloudinary bucket.

2. In-Memory State Synchronization:
The in-memory failover store does not synchronize state across multiple server
processes. Production must connect to a persistent MongoDB Atlas cluster.

A. ARCHITECTURE OVERVIEW
--------------------------------------------------------------------------------

NextCampus is engineered as a decoupled, modern three-tier web application:
1. Presentation Tier (Client SPA):
   - React 18 Single Page Application compiled with Vite 5.
   - Executes client-side inside user web browsers.
   - Manages interactive GIS map rendering, real-time sensor dashboards, and
     reactive state.
2. Application & API Gateway Tier (Backend Compute):
   - Python 3.11 FastAPI asynchronous REST microservice running under Uvicorn.
   - Enforces RBAC permissions, validates payloads via Pydantic, and executes
     institutional business rules.
   - Dual-mounted routes on `/api/v1` and `/api` ensure complete client compatibility.
3. Data & Persistence Tier:
   - MongoDB 7.0+ document database providing schema flexibility for spatial,
     IoT, and maintenance records.
   - Accessed asynchronously using the non-blocking Motor driver.
   - Includes a thread-safe in-memory mock store providing 100% test decoupling
     and graceful offline resilience.

D. COMPONENT ARCHITECTURE & LAYER BOUNDARIES
--------------------------------------------------------------------------------

1. Client Presentation Layer (`src/`):
- Pages (`src/pages/`): Full views mapped to routes in `App.jsx`.
- Components (`src/components/`):
  * Layout: `AppLayout`, `Navbar`, `Sidebar`, `MobileNav` managing responsive viewports.
  * Common: UI atomics (`Button`, `Card`, `Badge`, `Modal`, `Table`, `Tabs`).
  * Map: `CampusGisMap` managing Leaflet map tiles, polygon bounding boxes, and markers.
- Context: `AuthContext.jsx` manages user credentials, token persistence, and role guards.
- Service Adapter: `src/services/api.js` encapsulates network fetch calls and token injection.

2. API Gateway & Middleware Layer (`backend/app/main.py`):
- Route Registration: Symmetrical mounting on both `/api/v1` and `/api`.
- Exception Normalization: Catches exceptions and returns standardized JSON envelopes.
- Upload Server: Serves local files from `server/uploads` at `/uploads`.

3. Business Service Layer (`backend/app/services/`):
- Decoupled from HTTP: Functions accept Python dictionaries or primitives and return
  clean data objects, never touching FastAPI `Request` or `Response` objects.
- Testable: Enables automated unit and integration tests to verify business logic
  directly without spinning up mock HTTP servers.

4. Data Layer (`backend/app/db/`):
- Asynchronous Driver: Motor client pools connections.
- Seed Pipeline: Canonical initial records auto-seeded if collections are empty.
- Resilient Store: `IN_MEMORY_*` data structures provide seamless failover.

G. API ARCHITECTURE & DUAL MOUNTING
--------------------------------------------------------------------------------

NextCampus employs a dual-mounting architectural pattern in `backend/app/main.py`:
- Canonical Prefix: `/api/v1` (e.g., `/api/v1/campus/locations`)
- Compatibility Alias: `/api` (e.g., `/api/campus/locations`)
Both prefixes point to the identical router instance generated by `create_api_router()`.
This prevents broken links whether the client or external third-party calls the
versioned or unversioned route.

H. SOURCE CODE ARCHITECTURE
--------------------------------------------------------------------------------

Map of Major Directories and Their Responsibilities:
- `backend/app/main.py`: Application entry point, lifespan hooks, CORS, and exception handlers.
- `backend/app/api/routes/`: Route controllers receiving HTTP traffic.
- `backend/app/core/`: Configuration (`config.py`), logging (`logging.py`), security (`security.py`).
- `backend/app/db/`: Motor database connection (`connection.py`) and seed data (`seed_data.py`).
- `backend/app/schemas/`: Pydantic input/output schemas enforcing strict typing.
- `backend/app/services/`: Pure business logic decoupled from HTTP frameworks.
- `backend/tests/`: Pytest integration test workflows validating all system features.
- `server/`: Legacy Node.js Express server maintained for architectural reference.
- `src/`: Client React 18 source code (pages, components, tokens, services).
- `dist/`: Compiled production assets generated by Vite for Vercel deployment.
- `docs/`: Master documentation system.

I. SECURITY ARCHITECTURE & TRUST BOUNDARIES
--------------------------------------------------------------------------------

1. Trust Boundaries:
- Untrusted Zone: Client browser environment. All incoming data (parameters, bodies,
  headers) is treated as untrusted and strictly validated by Pydantic schemas.
- DMZ / Gateway Zone: FastAPI server handling rate limiting, CORS filtering, and JWT verification.
- Trusted Zone: Backend service layer, Motor database client, and MongoDB Atlas.
- Secret Isolation: Database credentials (`MONGODB_URI`) and hashing secrets (`JWT_SECRET`)
  remain strictly inside the Trusted Zone and are never exposed to the browser.

2. Access Control Matrix:
+---------------------+---------+-------+-------+------------+
| Resource / Action   | Student | Staff | Admin | Unauth     |
+---------------------+---------+-------+-------+------------+
| View Campus Map     | Yes     | Yes   | Yes   | Yes        |
| View SmartRooms     | Yes     | Yes   | Yes   | Yes        |

J. FAILURE POINTS & RESILIENCE STRATEGIES
--------------------------------------------------------------------------------

1. Database Unavailability:
- Behavior: Connection attempts time out after 2000ms.
- Mitigation: Server logs a warning and automatically switches to the in-memory
  mock store (`IN_MEMORY_*`). The application continues running without crashing.

2. External AI API (Google Gemini) Outage:
- Behavior: HTTPX request times out or returns HTTP 429/500.
- Mitigation: Service catches the exception cleanly and routes the query to the
  internal Multi-Intent Heuristics Engine v4.5, ensuring uninterrupted student assistance.

3. Frontend Network Dropouts:
- Behavior: Browser fails to reach direct backend port.
- Mitigation: `src/services/api.js` automatically retries through Vite's local
  proxy before throwing a user-friendly network error dialog.


--------------------------------------------------------------------------------
K. ARCHITECTURAL DECISIONS RECORD (ADR)
--------------------------------------------------------------------------------

1. Decision: Dual-Prefix Symmetrical Routing (`/api/v1` and `/api`):
   - Rationale: Prevents path mismatches between legacy client components and
     modern REST v1 endpoints.

2. Decision: Python FastAPI as Primary Engine:
   - Rationale: High async concurrency, automatic OpenAPI Swagger generation,
     strict Pydantic validation, and seamless future Python AI integrations.

3. Decision: Decoupled In-Memory Fallback Store:
   - Rationale: Enables complete automated test execution in headless CI environments
     without requiring a live MongoDB daemon.
